# Design: fix-amount-invalid-input

## Context

动机见 proposal.md - Why。相关约束：

- 金额框是 `type="text"` 自定义过滤输入（非 `type="number"`），过滤规则允许 `-` 留在首位，因此 `-`、`.`、`-.` 这类中间态会真实存在于 `posting.amount` 字符串里。
- 前端用 `decimal.js` 解析金额；`new Decimal('-')`、`new Decimal('.')` 会抛 `DecimalError`。由于 `-` 是 truthy，现有 `p.amount || 0` 兜底不生效。
- 抛错发生在渲染期（`canSubmit` → `isBalanced` 在模板 `:disabled` 中被求值），因此直接白屏。
- 现有关键点：`isBalanced`、`addPosting` 里各有一处 `new Decimal(p.amount || 0)`；`canSubmit`、`canAddPosting` 用 `p.amount` 的 truthiness 判断"已填写"。
- 编辑态分录 ≥ 2 条，故 `isBalanced` 不会提前 return，编辑页必现；新建态加到第 2 条分录后同样必现。

## Goals / Non-Goals

**Goals:**
- 任何金额输入中间态都不得让表单崩溃（消除渲染期 `DecimalError`）。
- 非法（非空且不可解析）金额有明确错误态（红色轮廓），且不可提交。
- 提交条件收紧为：所有金额非空且合法 + ≥2 笔有效分录 + 日期/成员已填 + 金额之和为零。

**Non-Goals:**
- 不改后端金额校验、DTO 或 API。
- 不拦截用户输入（不在输入时强制纠正文本），只标记与拦截提交。
- 不改动其他页面（BudgetView、SavingPlanView 等）的金额输入实现。

## Decisions

### D1: 引入容错解析 helper，返回 `Decimal | null`，替代 `new Decimal(amount || 0)`
新增一个模块内 helper（如 `parseAmount(text): Decimal | null`），空串与非法文本一律返回 `null`；`isBalanced` 与 `addPosting` 改用它，遇到 `null` 视为不参与求和 / 直接判为不平。

理由：崩溃根因是渲染期无条件解析；让"合法性判定"与"求和"共用同一口径，既根治崩溃又避免出现"某处能解析、某处不能"的分裂。`isBalanced` 用 `null` 短路返回 `false`，保证非法金额永不被当成 0 而误判平衡。

**被否决的备选**：用 `try/catch` 包住 `new Decimal(...)` 并在异常时当 0 —— 否决，因为 `-` 会被当 0 参与求和，可能出现 `-` + `0` 求和为 0 却通过校验、最终把非法串提交给后端；属于隐藏缺陷而非修复。

### D2: 合法性口径为「可选前导负号 + 至多一个小数点 + 至少一位数字」，空串单列为「未填」
用正则（`^-?(\d+(\.\d*)?|\.\d+)$` 语义）判定：`-5`、`5`、`5.`、`.5`、`0` 合法；`-`、`.`、`-.`、`-` 结尾等非法；空串不标红，只视为未填写。

理由：与 `decimal.js` 可解析集合对齐（只拦真正会抛异常的文本），同时覆盖用户逐字输入 `-5` / `.5` 的自然中间态。空串本就是"未填"语义，标红会让"刚打开表单"看起来像出错。

**被否决的备选**：要求必须数字开头、必须两位小数 —— 否决，明显恶化输入体验且超出缺陷修复范围。

### D3: 非法金额统一视为「未填写」，同时禁用提交与「添加分录」
`canSubmit` 与 `canAddPosting` 都改为要求每条分录金额"非空且合法"。金额输入框在「非空且非法」时加错误态 class（红色轮廓，`border-color: var(--color-expense)`，项目已有该色值）。

理由：与 `canAddPosting` 既有的"存在未填完的分录时不允许再添加"意图一致；顺带把"非法金额时点击添加分录触发同一处 `Decimal` 崩溃"这条路径一并堵死（按钮禁用）。用户需求"非法不可提交"也由此直接满足。

**被否决的备选**：只在 `canSubmit` 拦截、`canAddPosting` 维持 truthiness —— 否决，因为 `addPosting` 仍要处理非法串，自动配平口径变得含糊，且保留了一个崩溃入口。

### D4: 保留 `onAmountInput` 的过滤逻辑，仅新增非法标记
不改变"允许中间态文本"的现状，只在渲染时根据合法性加 class。

理由：用户明确要求"标红框"而非硬阻断输入；若在输入时就地纠正（如单独 `-` 自动清空），用户反而无法正常输入负数。

**被否决的备选**：把输入框换成 `type="number"` 依赖浏览器校验 —— 否决，浏览器对 `-`/`.` 的表现不一致，且会改变现有统一的金额输入交互与样式。

## Risks / Trade-offs

- [仅红框可能不够显眼，用户不知为何不能保存] → 保持最小改动，确认按钮禁用即为反馈；如需文案提示可作为后续独立改动。
- [前端正则口径比后端宽松] → 保持宽松，只拦 `decimal.js` 无法解析的输入；后端校验仍是最终权威。
- [非法当未填时，"自动配平"基于部分合法金额计算，可能填入看似合理的值] → 非法/未填状态下本就不可提交，不会持久化，可接受。
- [行为收紧可能影响既有测试/交互预期] → 现有测试未覆盖非法金额；新增用例覆盖标红与禁用两条路径。

## Migration Plan

纯前端行为修复，无数据迁移、无 API 变更。发布即生效；回滚即恢复旧行为（会重新引入白屏崩溃），因此不建议回滚。
