# Design: restore-view-state-on-detail-close

## Context

现状：交易页与日历页各自把交易列表（及日历页的日历网格）包在 `<template v-if="!showFormOverlay">` 中，交易表单覆盖层打开时整块内容被从 DOM 卸载：

- 交易页的滚动容器 `.transaction` 被清空，`scrollHeight` 归零，浏览器把 `scrollTop` 裁剪为 0；重新挂载后停在顶部，即最新交易。
- 日历页的 `CalendarGrid` 被重建，其内部的 `currentDate` ref 重新初始化为今天，显示月份跳回当月；而 `selectedDate` 位于 `CalendarView`、并未丢失，于是可能出现「选中日在另一月」的错位。

覆盖层本身已是 `position: absolute` 且不透明地盖满 pane，容器在打开时也已通过 `no-scroll` 切成 `overflow: hidden`；组件卸载并非覆盖层正常工作的必要条件。外层 shell 用 `v-for` 把各 pane 一直挂载，因此页面切换本就不丢状态——问题只出在覆盖层打开这一路径。目标与动机见 proposal.md。

## Goals / Non-Goals

**Goals:**
- 覆盖层关闭后，底层视图回到打开前的位置：交易列表滚动位置不变、日历显示月份与选中日期不变。
- 机制对「编辑 / 新建」两种打开方式与「取消 / 保存 / 删除」三种关闭结果表现一致。

**Non-Goals:**
- 不做「把新增/编辑的记录滚入视口」之类的智能定位。
- 不改 shell 的页面切换（已天然保留状态）。
- 不引入前端路由或历史栈。
- 不改变筛选条件变化时「列表滚动重置到顶部」的既有行为。
- 不做覆盖层内的焦点管理增强，仅在底层加交互屏蔽。

## Decisions

### D1: 保持底层内容挂载，用覆盖层覆盖而非卸载

覆盖层打开时不再移除底层列表/日历，改为保留在 DOM 中（`v-show` 式隐藏或直接保留，由不透明覆盖层遮盖）。这样滚动位置与 `CalendarGrid` 的月份状态无需任何存取代码即可自然保留。

理由：浏览器本就维护滚动位置与组件内部状态，卸载再重建是这份状态丢失的唯一原因；保留挂载等于零记账。

被否决的备选：显式保存-恢复（打开时记录 `scrollTop` 与 `currentDate`，关闭后在 `nextTick` 还原）。否决原因：重复浏览器已维护的状态；需处理内容长度变化时的裁剪与还原闪烁；两条打开路径 × 多种关闭结果的样板代码更多，收益不成比例。

### D2: 覆盖层打开时屏蔽底层交互

覆盖层已绝对定位且不透明，视觉上完全遮盖底层；继续保留 `no-scroll`（`overflow: hidden`）防止容器被程序化或滚轮滚动。额外对底层容器施加交互屏蔽（优先 `inert`；不支持时退化为 `aria-hidden="true"`），避免 Tab 焦点或辅助技术落入被遮盖内容。

被否决的备选：仅靠视觉遮盖。否决原因：键盘与屏幕阅读器仍能进入底层，形成焦点陷阱与可访问性缺陷。

### D3: 日历显示月份仍由 CalendarGrid 内部持有

不把 `currentDate` 上提为 prop / v-model，也不放进 store：既然网格不再被重建，其内部状态即可跨越覆盖层往返。

被否决的备选：将月份状态上提到 `CalendarView` 或用 store 持久化。否决原因：只有需要「跨组件重建」保留时才必要，而本变更正是消除重建；上提只会增加耦合与样板。

### D4: 数据变更后仍按「打开前的位置」恢复

store 的 `create/update/remove` 就地修改列表（create 前插、update 重排、remove 过滤），日历页另有 `dataVersion` watcher 重载当日数据；这些都不改变滚动容器本身。关闭覆盖层后仍恢复打开前的滚动位置与月份，内容长度变化（如新增一条导致总高度变化）交给浏览器的裁剪规则处理。

被否决的备选：保存后定位到被编辑/新增的记录。否决原因：会把「纯查看后关闭」与「编辑保存后」变成两种行为，增加状态分支且非本需求所求。

### D5: 与筛选条件变化的既有行为隔离

`lazy-load-transactions` 规定筛选条件变化后列表滚动重置到顶部，该路径由筛选抽屉触发、不会卸载列表。本变更不触碰它。

被否决的备选：由 store 统一管理「滚动位置策略」。否决原因：为一个小范围修复引入全局策略，复杂度与收益不成正比。

## Risks / Trade-offs

- 覆盖层打开期间多保留一份底层 DOM → 可忽略（列表/日历本就长期挂载，且属同一 pane 内容）；若将来出现超长列表的内存/布局顾虑，可回退到 D1 的显式保存-恢复方案。
- `inert` 的旧浏览器兼容性 → 做特性检测，不支持时以 `aria-hidden="true"` 加视觉遮盖兜底。
- 现有测试可能隐含「打开覆盖层后列表被移除」的假设 → 检查 `TransactionView.spec.ts` 与 `CalendarViewRefresh.spec.ts` 未见此类断言；新增往返场景测试时以保留挂载的语义为准。
- `v-show` 保留组件会保留其内部 watcher（如 `CalendarGrid` 的 `visibleRange`）→ 覆盖层打开期间月份未变，watcher 不会触发额外请求，符合预期。

## Migration Plan

纯前端行为修复，无数据、API 或 schema 迁移，发布即生效。回滚只需还原相关组件的渲染改动。
